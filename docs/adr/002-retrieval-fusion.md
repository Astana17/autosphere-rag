# ADR 002: Hybrid Retrieval Fusion Strategy

- **Status:** Approved
- **Date:** 2026-07-12
- **Author:** Founding ML Engineer

## Context

Neither retrieval signal alone is good enough on this corpus: TF-IDF lexical search scores recall@5 = 0.500 on the 15-question ground truth, FAISS embeddings score 0.833 (both below or near the 0.75 target). The two fail on different kinds of questions — TF-IDF struggles with paraphrased/colloquial questions that don't share legal vocabulary with the source article; embeddings occasionally rank a semantically-close-but-wrong chunk over the exact one. Combining them should, in principle, recover hits either signal misses alone.

## Options Considered

### Option 1: Unweighted Reciprocal Rank Fusion over a `top_k`-scaled candidate pool
The first implementation: for each of the two rankers, fetch a candidate list sized `max(top_k * 8, 30)`, then fuse by `score = sum(1 / (k + rank + 1))` across both lists with equal weight, and return the top `top_k` of the fused result.
- **Pros:** simple, standard RRF, no score-scale normalization needed since it operates on rank position.
- **Cons (both found by actually running the service, not by the eval script):**
  1. **Candidate pool tied to `top_k` breaks prefix-consistency.** `retrieve(q, top_k=5)` and `retrieve(q, top_k=10)` fetched *different-sized* candidate pools, so the first could return a genuinely different top result than the first 5 items of the second — not just a truncation. `evaluation/evaluate_retrieval.py` always calls `top_k=10` and slices to 5 for recall@5, so its reported number wasn't provably what a live `/ask?top_k=5` call would return.
  2. **Unweighted fusion lets a mediocre-in-both-signals chunk beat an excellent-in-one-signal chunk.** Manually asking the live service a realistic, informal question — "я выпил алкоголь за рулем, если остановят, то какие последствия?" (no legal vocabulary at all) — returned a chunk about overtaking rules, completely off-topic. Diagnosis: FAISS correctly ranked the right statute (Статья 619-1) #1; TF-IDF, working from a query with zero shared vocabulary with the statute text, ranked it ~109th (still a real rank, not absent, but numerically weak) — outside the 100-item candidate pool the code used at the time, so it contributed no lexical RRF score at all. Meanwhile an unrelated chunk that merely limped into both truncated lists at moderate ranks (12th and 39th) out-scored it. Unweighted RRF assumes both signals are equally trustworthy for every query; that assumption is false here.

### Option 2: Full-corpus ranking + weighted RRF (0.3 lexical / 0.7 embeddings)
Rank the entire corpus (not a truncated pool) in both signals — cheap at ~2,700 chunks, since TF-IDF cosine similarity is already computed as a full array and FAISS's `IndexFlatIP` is exact brute-force search regardless of `k`. Fuse with `score = 0.3 / (k + lex_rank + 1) + 0.7 / (k + emb_rank + 1)`, and only truncate to `top_k` at the very end.
- **Pros:** every chunk has a real rank in both signals (nothing is "absent"), which removes candidate-pool truncation as a failure mode entirely; `retrieve(q, top_k=N)` is a strict prefix of `retrieve(q, top_k=M)` for any `N < M`, by construction; the 0.7/0.3 weighting reflects the two signals' actual, measured reliability on this corpus (embeddings recall@5 0.833 vs. lexical 0.500 alone) instead of pretending they're equally trustworthy.
- **Cons:** weighting is a global constant tuned on this corpus and this ground truth — it isn't re-derived per query, so a query where lexical genuinely is the stronger signal (see Consequences) can still lose to embeddings' bias.

## Decision

**Option 2** — full-corpus ranking, weighted RRF (`LEXICAL_RRF_WEIGHT = 0.3`, `EMBEDDING_RRF_WEIGHT = 0.7`, `RRF_K = 60`), implemented in `app/retrieval.py::VectorRetriever._reciprocal_rank_fusion` and its call site in `retrieve()`.

## Consequences

- **Ground-truth recall@5:** 0.767 (unweighted, truncated pool) → 0.900 (full-corpus, weighted). MRR improved 0.622 → 0.717 and nDCG@10 improved 0.709 → 0.753 — the weighting change wasn't a strict trade against the formal ground truth, it improved average rank quality too.
- **One formal ground-truth question regressed:** "Что означает термин «уступить дорогу»..." went from a hit to a miss, because for that specific query TF-IDF ranked the correct chunk #1 while embeddings ranked it ~55th — down-weighting lexical to 0.3 handicapped a case where lexical actually had the better answer. This is the honest cost of a global weight: it's tuned for the corpus on average, not per-query, so some individual queries where the down-weighted signal was actually right will lose ground. Accepted because the alternative (equal weighting) was demonstrably broken on realistic, informally-phrased questions, which is what defense and real users will actually type.
- **The colloquial drunk-driving question now retrieves correctly:** all top-5 results are on-topic (Статья 619-1, Статья 440, Пункт 12, Статья 608), where the unweighted version returned an unrelated overtaking-rules chunk as its top hit.
- **Latency:** negligible change — TF-IDF full-array cosine similarity and FAISS exact search over ~2,700 chunks are both sub-millisecond regardless of how many results are requested; ranking the full corpus instead of a 100-item pool didn't produce a measurable difference locally.
- **Known limitation carried forward:** a fixed global weight is a coarse instrument. A per-query confidence-aware fusion (e.g., down-weighting a signal further when its own top score is very low, which is a legitimate proxy for "this signal found nothing relevant") would likely recover the one regressed ground-truth question without re-breaking the colloquial one, but was out of scope for this pass — noted here rather than silently left for someone to rediscover.
- **Known limitation, found after this fix and deliberately left unfixed:** weighting and pool-truncation fixes only help when *some* signal ranks the right chunk reasonably well. They don't help when the right answer requires bridging vocabulary that never co-occurs anywhere in the corpus at all. Example, found by manually asking the live service "что будет если проехать на оранжевый светофор?" (what happens if you drive through an orange/yellow light?): the correct answer is scattered across three separate provisions in two documents — ПДД Пункт 24 (defines what a yellow signal means), ПДД Пункт 36 (says drivers must stop at a "запрещающий сигнал"), and КоАП Статья 599 (the fine, titled "Проезд на запрещающий сигнал светофора"). None of the three ever uses the word "оранжевый," and the connection "yellow → prohibiting signal → penalty" is domain knowledge, not shared vocabulary. Measured directly: Статья 599 ranks 766th under TF-IDF and 66th under embeddings for this query — both retrieval signals genuinely fail to surface it in a useful top-k, so no amount of `top_k` tuning or reweighting on the current architecture fixes this class of question. The real fix is query rewriting: use the LLM itself to reformulate the user's colloquial question into legal terminology (e.g., "проезд на запрещающий сигнал светофора, административная ответственность") *before* retrieval, then retrieve on the rewritten query. That's a real architecture change — an added LLM call in the critical path, with its own latency and token cost, and its own regression-testing burden (would need re-running the full 15-question ground truth through the rewriting step to confirm it doesn't itself introduce drift). Deliberately not implemented in this pass; recorded here as the concrete next step rather than left for someone to rediscover from scratch.
